01

自我介绍

一边读着法律，回过神来却已经在运维服务器。凡是感兴趣的事，我总会先动手试试看。

我是中央大学法学院法律学系四年级学生，在修读法律学的同时，也作为一台 Minecraft 服务器的运营成员参与基础架构管理。

最初接触服务器管理其实相当偶然：当时我所在的那台服务器，运营方难以为继，而恰好手头资金还算宽裕的我便顺势租下一台 VPS，接手了管理。后来稳定成用一台旧笔记本电脑跑的家庭服务器，起步时连 Dynmap 都没有，是从最精简的配置开始的。我从很早以前就对网络攻击的类型和手法感兴趣，而在为成员们一个个添加功能的过程中，逐渐发现这份兴趣和服务器管理这个角色相当契合。「想为大家提供更好的东西」的心愿，与「每当对外开放的范围扩大一分，就把安全漏洞逐个堵上」这种基础架构安全特有的、类似解谜的乐趣彼此咬合，让我感到强烈的好奇心与成就感。如今，包含安全在内的基础架构工程整体，已是我关注的核心。

对法律的兴趣，追根溯源同样来自对安全的关注。我原本也考虑过报考工学院，但在了解到 Winny 案之后，我感到那起围绕软件开发者的案件，与安全工程师的处境是相通的。要防御攻击，就必须深入理解攻击手法本身，攻防本是一体两面。意识到这类技术人员与研究者需要有人从法律层面提供支撑，正是我对法学产生兴趣的起点。再加上在实际参与服务器规则的条文化工作时，我被那些为避免歧义而反复斟酌的法律用语，以及严谨之余又带着几分人情味的条文解释之争所吸引，于是决定作为一名法学学子正式研习法律。

我看重的是，对于感兴趣的事绝不将就。对法律感兴趣，就进法学院去学；对服务器基础架构感兴趣，就真的把服务器搭起来，还去尝试虚拟化。就这样，我一直循着兴趣不断行动。这背后始终有一股「为了他人」做点什么的强烈念头——无论是为成员改进服务器，还是成为一名支撑安全工程师的法律人这一未来图景，都以这份念头为原点。

我看重的事

  • Men for others, with others

    无论是为成员打理好服务器环境，还是立志成为一名支撑安全工程师的法律人，其原点都是那份「为了他人、与他人同在」的心愿。

  • 忠于好奇心

    对于感兴趣的领域，无论有无经验，我都看重亲身踏进去试一试。无论是选择人生方向还是技术选型，我都以这一态度为准绳作出判断。

  • 法治

    这是我在研习宪法学的过程中扎下根的观念。在服务器规则里，我对运营方自身的权限也设下严格的制约；在基础架构上，则用 Tailscale 的 ACL 明确划清「谁、在多大范围内、能做什么」。不分领域，凡权力与权限必受约束——我把这一理念落实到了实务当中。

项目实绩

从服务器运营与个人开发中，选取可以公开的 4 件列出。

Minecraft 服务器基础架构搭建与运维

将两台家庭服务器组成 Proxmox 集群，连同访问控制一起搭建并运维 Minecraft 服务器及周边服务

角色
负责服务器搭建与基础架构管理
期间
2022年11月 — 至今

起初只是在一台 Ubuntu 机器上装好服务端软件，后来意识到需要按成员、运营团队、我本人（管理员）这三类使用者分别理清「开放到哪一层访问」，于是自 2026 年 3 月起迁移到基于 Proxmox VE 的虚拟化环境。玩家通信走中继服务器加 Tailscale VPN，面向运营的 Web 服务走 Cloudflare Tunnel，管理操作走 Tailscale——按路径分离防护方式。还搭建了监控体系（Prometheus / Grafana，7 种告警），并引入 Crafty Controller 等 GUI 工具，让整个团队都能参与管理。

  • 自 2022 年起持续运营一个约 30 人规模的社群
  • 将两台物理机组成 Proxmox 集群，按用途拆分为 7 台以上的 LXC 与 VM
  • 即便「外面没人在看」，也不偷工减料，打造稳固的环境

技术栈

  • Proxmox VE
  • LXC / VM
  • Tailscale
  • Cloudflare Tunnel
  • Nginx Proxy Manager
  • Prometheus / Grafana
  • Crafty Controller

OpsBot — 运营业务自动化 Discord Bot

将服务器运营中的报备、投票、许可申请、催办等事务处理自动化的 Discord Bot

角色
设计与实现（个人开发）
期间
2026年9月 — 至今

把服务器内日常发生的报备受理、投票实施、记名许可、催办通知等事务处理，做成可以在 Bot 的命令与表单中一站式完成。采用两层结构实现：Cloudflare Workers（TypeScript）加 D1 作为 API 与数据管理层，运行在 Proxmox 上的 Python 轮询器持续监视 Discord 的消息与表情回应，以触发各项处理。由于 Cloudflare Workers 免费额度限制 cron 任务最多 5 条，我把催办检查、台账更新等多个批处理合并到一条 cron 中调度执行，在额度之内实现了功能。凡是需要作出批准、驳回等判断的处理，一律以人的输入为起点；LLM（Claude）仅用于检测申请内容的疏漏、给出任务分配候选等「人工容易遗漏的检测」。目前任务的自动检测与分配功能正处于试运行（影子模式）验证中——检测结果仅记入日志，并不实际发出通知。

  • 将报备受理、投票、许可、催办等多项事务处理命令化并自动化
  • 以 Cloudflare Workers（TS）加 D1、以及 Proxmox 上的 Python 轮询器构成两层结构实现
  • 在 Workers 免费额度仅 5 条 cron 的限制下，设计出将多个批处理归并为一条的调度方案

技术栈

  • Cloudflare Workers（TypeScript）
  • D1
  • Python（运行在 Proxmox CT 上的轮询器）
  • Discord API
  • Claude Code CLI

REWIS（全球铁道信息系统）

在不断扩张的线路网中消除「不知道该怎么走」的困扰，宛如现实换乘查询的 Web 应用

角色
设计与实现（个人开发／数据由各铁道公司即参加者陆续提供）
期间
2025年10月 — 至今

随着 Minecraft 内的铁道网不断扩张，出现了不逊于现实铁道公司的线路图，与此同时「不知道坐哪条线才能到目的地」的参加者也越来越多，我因此着手制作。需要在 GitHub Pages 这种静态站点的限制下实现登录与数据写入，于是把最初用仓库内 JSON 管理的数据，改为以 Cloudflare Workers 作为外部正本的方式，搭建出让各铁道公司（参加者）从运营方页面直接编辑数据的机制。一边研究既有的换乘查询服务，一边通过 PWA 支持，力求兼顾类似应用的操作手感与 PC 端显示。

  • 在静态站点上实现了以 Cloudflare Workers 为外部正本的数据编辑功能
  • 目前支持 7 条线路 34 个车站，今后计划扩大到约 50 条线路、约 200 个车站的规模
  • 通过 PWA 支持，兼顾类似应用的操作手感与 PC 端显示

技术栈

  • HTML
  • CSS
  • JavaScript（原生）
  • GitHub Pages
  • Cloudflare Workers（外部数据正本与编辑 API）
  • PWA
